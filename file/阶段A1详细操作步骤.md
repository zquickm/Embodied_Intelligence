### 2.4 过拟合点在哪（验收标准 4 的依据）

跑 15 epoch（seed 7）观察过拟合：

| epoch | train loss | val loss | 现象 |
|---|---|---|---|
| 1 | 0.1860 | 0.0613 | 欠拟合 |
| 7 | **0.0116** | **0.0305** | **val loss 最低，最优点** |
| 9 | 0.0069 | 0.0508 | **val loss 回升 ↑** |
| 15 | 0.0047 | 0.0654 | val loss 持续变差，train loss 仍降 |

**过拟合点在第 7 epoch 附近**：从第 8 轮起 train loss 还在降（0.0116 → 0.0047），但 val loss 从 0.0305 涨到 0.0508。**这就是"训练集上越来越好、泛化越来越差"的定义。**

**注意一个容易误判的地方**：val loss 在第 4 和第 6 轮也有小幅回升（0.0501、0.0356），那不是过拟合，是**验证集只有 5000 张**带来的采样噪声。**判断过拟合要看趋势，不要看单点波动。** 区分方法：真正的过拟合在 val loss 回升时 train loss 一定还在降；噪声波动则是两者同向。

### 2.5 一个反直觉的实测结果：MNIST 上 AMP 没有加速

同一份代码，开/关 AMP 对比（2 epoch，seed 0）：

| 配置 | test acc | 每 epoch 耗时 |
|---|---|---|
| AMP 开启 | 98.75% | **7.1 s** |
| AMP 关闭 | 98.81% | **6.4 s** |

**AMP 反而慢了约 11%。**

**为什么**：这个模型只有约 42 万参数，卷积计算量太小，fp16 的吞吐优势体现不出来，反而多了 GradScaler 的 scale/unscale 开销。**AMP 的收益在模型大、计算密集时才出现**（典型场景是 Transformer 或大卷积网络）。

**这不是 bug，是边界条件。** 验收标准 3 要求"能解释 AMP 解决了什么问题"，正确的回答不是"AMP 更快"，而是：**AMP 解决的是 fp16 数值范围不足导致梯度下溢的问题（靠 GradScaler），并用 fp16 减少显存带宽压力；但它有固定开销，小模型上净收益可能为负。** 能不能说出这个边界，比会不会写 `autocast` 更能体现理解。

## 3. 这一阶段要建立的核心认知

训练循环有五件事必须自己做，每一步都对应一个具体问题：

| 步骤 | 代码 | 不做的后果 |
|---|---|---|
| 1 | `optimizer.zero_grad()` | 梯度累加，等效学习率失控 |
| 2 | 前向 `model(x)` | 没有预测 |
| 3 | 损失 `criterion(out, y)` | 没有优化目标 |
| 4 | 反向 `loss.backward()` | 没有梯度 |
| 5 | 更新 `optimizer.step()` | 参数不变，白算 |

**`zero_grad()` 为什么必须在 backward 前**（验收标准 2 的答案要点）：

PyTorch 的 `.grad` 是**累加**语义，不是覆盖。`backward()` 把新算出的梯度**加到**已有 `.grad` 上。如果不清零，第 N 步的梯度 = 前 N 步梯度的和，更新幅度会越来越大且方向错乱。

值得注意的细节：`zero_grad()` 放在 backward 前或 step 后**在数学上等价**（都是"下一次 backward 前梯度为零"）。放在 backward 前更常见，因为它把"清空—前向—反向—更新"四步放在一起，读起来是一个完整周期。真正的错误是**完全不调**或**在 backward 之后、step 之前调**（那等于把这一步的梯度也清了，参数不会更新）。

**AMP 解决了什么**（验收标准 3 的答案要点）：

- `autocast`：让部分算子（矩阵乘、卷积）用 fp16 算，减少显存带宽压力、提高吞吐；其余算子（如 softmax、loss）仍用 fp32 保证数值稳定。
- `GradScaler`：**这是 AMP 的必要配套**。fp16 能表示的最小正规数约 6e-5，小梯度会下溢成 0，训练直接停滞。GradScaler 先把 loss 乘一个大数（初始 65536）再 backward，让梯度落在 fp16 可表示范围内，step 前再除回来。若检测到下溢（inf/nan），会跳过着一步并降低 scale 因子。

**关键理解**：`autocast` 和 `GradScaler` 不是两个独立选项，**是配套使用的**。只开 autocast 不开 scaler，梯度下溢会让训练无声失败（loss 不降，但不报错）。

## 6. 踩坑与注意

### 6.1 ⚠️ 分段代码拼接导致函数误入类作用域（本阶段实际踩到）

**现象**：

```
NameError: name 'build_loaders' is not defined
```

**第一反应**：以为漏抄了一整段函数。

**实际原因**：代码是分 5 段给的，第 2 段的 `def build_loaders(args):` 紧跟在 `class SmallCNN` 的 `forward` 方法之后。粘贴时缩进自然延续，**三个函数（`build_loaders`、`evaluate`、`train_one_epoch`）全部变成了 `SmallCNN` 的类方法**，模块级根本不存在 `build_loaders`。

**为什么难发现**：

- **语法完全合法**，`python -m py_compile` 不会报错
- 错误信息指向调用处（第 103 行），但问题在定义处（第 31 行），两个位置相距很远
- 在编辑器里肉眼看，缩进看起来"挺整齐"——因为它确实一致地多缩了 4 格

**确认方法**（10 秒）：

```powershell
python -c "import ast; t=ast.parse(open(r'文件路径',encoding='utf-8').read()); print([n.name for n in t.body if isinstance(n,(ast.FunctionDef,ast.ClassDef))])"
```

错误时输出：

```
['SmallCNN', 'main']        ← build_loaders 等不在顶层
```

正确时输出：

```
['SmallCNN', 'build_loaders', 'evaluate', 'train_one_epoch', 'main']
```

VS Code 里等价操作：`Ctrl+Shift+O`（转到符号），`build_loaders` 不出现在列表里就是缩进错了。

**根本教训**：**Python 靠缩进决定作用域，没有 `endif` 之类的结束标记。多段代码拼接时，缩进就是语义。** 只要上一段以类/函数内的行结尾，下一段的 `def` 就会自动继承缩进，静默变成嵌套定义。

**后续预防**：

1. 写完文件先跑上面那条 `ast` 检查，再运行
2. 我给多段代码时会明确标注每段的"顶格位置"
3. 写嵌套结构（如 D2 的 `class RSSM` 里套 `Prior`/`Posterior`）时**必须**用这个检查——层级越深越容易错

### 6.3 `num_workers` 在 Windows 上的问题

Windows 用 `spawn` 而不是 `fork` 启动子进程，DataLoader 设 `num_workers>0` 时如果脚本没有 `if __name__ == "__main__":` 保护，会无限递归创建进程。

**本阶段用 `num_workers=0`**：MNIST 数据小（60000 张 28×28），读盘不是瓶颈，多进程反而增加开销和出错面。

### 6.4 AMP 的 API 位置（torch 2.11）

`torch.cuda.amp.GradScaler` 仍可用但已是旧接口。**新写法是 `torch.amp.GradScaler("cuda")`** 和 `torch.amp.autocast("cuda")`。本机 torch 2.11 两者都支持，用新写法避免以后废弃警告。

### 6.6 val loss 抖动不等于过拟合

验证集只有 5000 张，一次误判就是 0.02% 准确率，loss 的采样噪声会被放大。

**本次实测**：seed2 的 val loss 在 epoch 3 涨到 0.0524、epoch 6 涨到 0.0517，但 test acc 仍有 0.99。

**判据**：真正的过拟合是 **train loss 还在降、val loss 持续升**（反向变化）；单点或小幅回升多是噪声。详见第 2.4 节 15 epoch 探针。
